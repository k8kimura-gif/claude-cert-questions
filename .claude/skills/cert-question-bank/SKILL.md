# 問題バンクの作問と検証

このリポジトリの問題は、受験者が本番の正誤の基準として覚えるものである。誤った正解を 1 つ載せると、その人は本番で同じ誤りをする。そのため、**記憶で書かず、公式ドキュメントの本文を開いてから書く**ことと、**確かめた範囲を正直に報告する**ことを、手順全体の軸にする。

Claude の API や Claude Code の仕様は変わるのが速く、学習時点の知識は古いことが多い。実際にこのバンクでは、もっともらしく書いた問題の 400 問中 13 問が現在のドキュメントと食い違っていた(`references/pitfalls.md` に一覧がある)。

## 前提

- 正本は `questions/<資格>/<分野>.json`。生成スクリプトは存在しない。JSON を直接編集する。
- 資格は `developer` と `architect` の 2 つで、問題を混ぜない。分野と配点は `exams/<資格>.json` にある。
- 問題 ID は変えない・再利用しない。利用者の学習記録が ID に結び付いているため。削除した ID も欠番のままにする。
- 文章は日本語(本番が日本語版のため)。API のパラメータ名、コマンド、ファイル名は原文のまま書く。
- Architect は全問がシナリオ問題で、`scenarioId` に `questions/architect/scenarios.json` の ID を入れる。Developer は `scenarioId: null`。

問題 1 件の形:

```json
{
 "id": "arch-agent-001", "cert": "architect", "domain": "<exams の分野 ID>",
 "type": "single", "scenarioId": "support",
 "stem": "問題文",
 "choices": [{ "id": "a", "text": "選択肢", "why": "これが正しい/誤っている理由" }],
 "answer": ["a"],
 "explanation": "解説。なぜそれが正解かを原則から説明する",
 "refs": ["https://… 正解を裏付けるページを先頭に"]
}
```

`type` は `single`(正解 1 つ)か `multi`(複数、問題文に個数を書く)。選択肢は 4 つ。`refs[0]` は検証のときに照合先になるので、正解の根拠がいちばん直接に書かれているページを置く。

## 作問の手順

1. **足りない分野を決める。** `node scripts/validate.mjs` が分野ごと・シナリオごとの問題数を出す。配点(`exams/*.json` の `weight`)に対して少ない分野と、問題数の少ないシナリオから埋める。
2. **出典のページを先に開く。** 扱う話題の公式ページを取得して読む(`platform.claude.com/docs`、`code.claude.com/docs`、`anthropic.com/engineering` の記事、`modelcontextprotocol.io`)。ドキュメントのページは URL の末尾に `.md` を付けると原文が取れる。ページが移転していたら新しい URL を使う。
3. **ページに書いてあることから問題を作る。** 問題は 2 種類ある。どちらを書いているかを意識する。
   - **事実を問う問題**: パラメータ名、フラグ、ファイルの置き場所、既定値、エラーコード、料金の倍率など。正解の文は、ページの記述と 1 対 1 で対応させる。数値は本文にあるものだけを使う。
   - **設計判断を問う問題**: 原則を具体的な場面に当てはめるもの。正解は、出典が述べる原則から素直に導けるものにする。出典にない経験則や数字(「ツールは 4〜5 個まで」など)を解説に足さない。
4. **誤答を作る。** 誤答は「その話題を半分だけ理解している人が選びそうなもの」にする。明らかに馬鹿げた選択肢は学習にならない。各選択肢の `why` に、なぜ誤りかを 1〜2 文で書く。別の文脈では正しい手法を誤答にするときは、この場面でなぜ不適切かを書く。
5. **ID を振って追記する。** その接頭辞(`dev-app-`、`arch-ctx-` など)の最大番号の次から、3 桁で振る。
6. **長さの偏りを測る**(下の「選択肢の長さ」)。
7. **検証する**(下の「検証の手順」を、追加した問題の ID に絞って行う)。自分で書いた直後の問題も例外にしない。書いた本人の確信は裏付けにならない。
8. `node scripts/validate.mjs` が通ることを確かめる。

### 選択肢の長さ

正解だけを丁寧に書くと、正解がいちばん長くなり、内容を知らなくても当てられる。初版では正解が最長の問題が約 9 割あった。

- `node scripts/length-bias.mjs` で、正解の長さの順位の分布を見る。目安は、1 位が 4 割以下で、4 位(最短)がほぼ 0 にならないこと、2 位に偏らないこと。
- `node scripts/length-gaps.mjs <資格> <件数>` は正解が最長の問題を、`length-second.mjs` は正解が 2 番目に長い問題を、差の小さい順に出す。
- 直すときは誤答を具体的に書き足して伸ばす(条件、理由、手段を加える)。正解を削って意味を弱めない。誤答だけをまとめて書き換えるには、`{ 問題ID: { 選択肢ID: 新しい文 } }` を `export const P` した差分ファイルを作り、`node scripts/apply-patch.mjs <ファイル>` を使う(正解の選択肢は書き換えを拒否する)。
- 日本語の文字数は目測が当たらない。書き換えたら必ずスクリプトで測り直す。

## 検証の手順

問題ごとではなく、**参照ページごと**に進める。同じページを根拠にする問題をまとめて見ると、ページを 1 回読めば済み、問題同士の矛盾にも気付ける。

1. **下準備。** `node scripts/verify-prep.mjs`(一部だけなら `--ids id1,id2`)。`.verify/` に次ができる(git には入らない)。
   - `index.tsv`: ページごとの問題数。多い順。
   - `claims/<キー>.txt`: そのページを第一参照にする問題の、問題文・正解・解説。
   - `pages/<キー>.txt`: ページ本文。
   「取得できない」「移転している」と出たページは、正しい URL を探して `refs` を直す。
2. **問題を 2 種類に分ける。** `claims/` を読み、各問題が事実を問うものか、設計判断を問うものかを分ける。
3. **事実を問う問題は、本文で裏付ける。** 主張を 1 行 1 件の照合ファイルにして `node scripts/check-claims.mjs <ファイル>` にかける。書式は `ラベル || 正規表現 || ページのキーの一部`。
   - `OK` は語が見つかっただけである。出力された前後の文を読み、問題の主張と同じ意味かを確かめる(否定文や、別の機能の説明に載っていることがある)。
   - `MISSING` は、書かれていないのか、正規表現が合っていないのかを本文を読んで判断する。書かれていなければ、その問題は裏付けがない。
   - 正解だけでなく、解説と各 `why` に書いた事実も対象にする。誤りは解説の「ついでの一言」に多い。
   - ページ全体を会話に読み込むと長すぎるので、本文は手元のファイルに置いたまま検索で当たる。記事のように論旨を追う必要があるページだけ、通読する。
4. **設計判断を問う問題は、原則と突き合わせる。** 出典が述べる原則を確認し、(a) 正解がその原則から導けるか、(b) 誤答のどれかが出典で推奨されていないか、(c) 解説が出典にない主張をしていないか、を見る。正解そのものは出典に書かれていないので、これは「矛盾しない」ことの確認であって、裏付けではない。
5. **`references/pitfalls.md` の項目に当たる問題がないかを見る。** 過去に実際に間違えた箇所の一覧である。新しい誤りを見つけたら、ここに追記する。
6. **直す。** 正解や解説の修正は JSON を直接編集する。裏付けが取れない主張は、言い切りを弱めるより、削るか、根拠のあるものに置き換える。問題として成り立たなくなったら、同じ ID のまま別の論点に差し替える。
7. **仕上げ。** `node scripts/validate.mjs` と `node scripts/length-bias.mjs` を実行する。main に push すると GitHub Actions が検証して公開する。push は依頼があったときだけ行う。

## 報告の形

確かめた範囲と、確かめられなかった範囲を分けて書く。「全問確認しました」とだけ書かない。

- 何問を、どのページと照合したか。
- 直した問題の一覧(問題、何が違っていたか、どう直したか)。
- 事実を問う問題で本文の裏付けが取れた数と、設計判断の問題で矛盾がないことを確認した数。この 2 つを合算しない。
- 確認できなかったもの(ページが書き直されて記述が消えた、出典が有料・非公開、など)。
- 照合したのは現在の公式ドキュメントであり、試験ガイドそのものではないこと。仕様変更の前の用語で出題される可能性は残る。
